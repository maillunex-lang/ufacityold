# Безопасность VPS (SSH)

## Бан по IP за подбор паролей (fail2ban)
Состояние на 2026-11-04: в журнале ssh непрерывный подбор паролей к `root`/`admin` с разных адресов (вход по паролю и под root разрешён, межсетевой экран ufw выключен). fail2ban был установлен; его настройки по умолчанию (5 попыток за 10 минут, бан на 10 минут) плохо ловят распределённый подбор «по 1–2 попытки с адреса».

**Включение (выполняет владелец под root):**
```
curl -fsSL https://raw.githubusercontent.com/maillunex-lang/ufacity/main/deploy/server/harden-ssh-ban.sh -o harden-ssh-ban.sh
cat harden-ssh-ban.sh        # прочитать
bash harden-ssh-ban.sh <ВАШ_IP>   # ваш адрес: whoami с сервера — `who am i` / в журнале «Accepted password … from <IP>»
```
Скрипт: делает копию настроек, пишет **только** `/etc/fail2ban/jail.d/lunexgame-sshd.local` для jail `sshd` (3 попытки за сутки → бан на сутки, повторно — дольше, до 4 недель), проверяет конфигурацию (`fail2ban-client -t`), при ошибке откатывает, перечитывает настройки и показывает статус.
- Откат: `rm /etc/fail2ban/jail.d/lunexgame-sshd.local && fail2ban-client reload`.
- Разбанить: `fail2ban-client set sshd unbanip <IP>`.
- Проверка через 10–30 минут: `fail2ban-client status sshd` (растёт «Total banned»), `journalctl -u fail2ban --since "1 hour ago" | grep Ban`.
- Если ваш адрес меняется (мобильный интернет), он не будет защищён списком исключений; держите второй способ входа (консоль провайдера).

## Что бан НЕ решает
- Распределённый подбор (по одной попытке с тысяч адресов) бан не остановит полностью. Надёжная защита — **вход только по ключам** (`PasswordAuthentication no`) и запрет входа под root по паролю. Это отдельный шаг с риском потерять доступ: сначала ключ и проверка второй сессией, затем отключение пароля (`sshd -t`, `reload`, не `restart`). Подготавливается отдельно по запросу владельца.
- Автодеплой использует ключ и не затрагивается банами (успешный вход по ключу не считается неудачей).

## Вход только по ключам (Termius, без запасного входа в консоль)
Первоначально считалось, что запасного входа нет; **по скриншоту панели хостинга (my.u1host.com, сервер Id 643405) 2026-11-04 в меню есть `VNC`, `Смена пароля` и `Rescue-режим`** — значит, страховка существует (перед применением нужно проверить вход через VNC по паролю root). Процедура всё равно построена так, чтобы ошибка не заперла сервер: ключ проверяется вторым окном **до** отключения пароля, а применение страхует таймер автоотката на 10 минут. Названия пунктов Termius ниже приблизительные (интерфейс меняется).

**Шаг 1. Два ключа.** В Termius: *Keychain → «+» → Generate key* (тип ED25519). Создайте **два** ключа: основной (например, `lunexgame-phone`) и резервный (`lunexgame-backup`). Резервный закрытый ключ экспортируйте (*Export*/*Copy private key*) и сохраните в менеджере паролей: если телефон потерян или Termius сброшен, вы импортируете его в Termius на другом устройстве. **Закрытые ключи никому не отправляйте, в том числе мне.** Публичные части — не секрет.

**Шаг 2. Добавить публичные ключи на сервер** (под root в текущей парольной сессии):
```
mkdir -p /root/.ssh && chmod 700 /root/.ssh
cat >> /root/.ssh/authorized_keys <<'KEY'
<публичный ключ lunexgame-phone — одна строка, начинается с ssh-ed25519>
<публичный ключ lunexgame-backup — одна строка>
KEY
chmod 600 /root/.ssh/authorized_keys
wc -l /root/.ssh/authorized_keys
```

**Шаг 3. Проверить вход по ключу.** В Termius создайте **второй** хост с тем же адресом, пользователь `root`, способ входа — ключ `lunexgame-phone`, пароль не указывать. Подключитесь **в новом окне**: должно открыться без запроса пароля. Затем так же проверьте резервный ключ (отдельным хостом). Первую (парольную) сессию **не закрывайте**.

**Шаг 4. Запустить скрипт** (в парольной сессии):
```
curl -fsSL https://raw.githubusercontent.com/maillunex-lang/ufacity/main/deploy/server/harden-ssh-keys.sh -o harden-ssh-keys.sh
cat harden-ssh-keys.sh
bash harden-ssh-keys.sh
```
Скрипт отказывается работать без ключей в `authorized_keys`, просит подтверждения (`yes`), пишет изменение в отдельный файл `/etc/ssh/sshd_config.d/00-lunexgame-hardening.conf` (`PasswordAuthentication no`, `PermitRootLogin prohibit-password`), проверяет `sshd -t` и что настройка действительно вступила в силу, ставит **таймер автоотката на 10 минут** и делает `reload` (текущие сессии не обрываются).

**Шаг 5. Подтвердить.** Не закрывая парольную сессию, откройте **новое** окно по ключу — должно получиться. Затем в первой сессии: `systemctl stop lunexgame-ssh-revert.timer` (подтверждение). Если что-то не так — подождите 10 минут, пароль вернётся сам; или сразу `rm /etc/ssh/sshd_config.d/00-lunexgame-hardening.conf && systemctl reload ssh`.

**Что не затрагивается:** автодеплой (вход по ключу с ограничением команды), другие проекты. **Не проверено на сервере** — скрипт проверен локально на заглушках (отказ без ключей, отмена, успех, перекрытие настройки), реальный `sshd` в среде разработки недоступен; сервер проверит `sshd -t` в момент запуска.

**Перед шагом 4 (обязательно):** откройте VNC в панели хостинга, убедитесь, что появляется приглашение входа, войдите по паролю root и выйдите (`exit`). Консоль работает локально и от настроек SSH не зависит. Не нажимать «Переустановить ОС» (стирает сервер целиком) и «Выключить» (останавливает все проекты).

**Заметка о хостинге:** в панели виден баланс 6,12 RUB при тарифе 497,41 RUB/месяц. Порядок списания и последствия нехватки средств не проверены — владельцу рекомендовано уточнить дату списания, иначе возможно отключение сервера и всех проектов на нём.
