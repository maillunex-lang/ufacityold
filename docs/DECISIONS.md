# Решения
## Утверждены заказчиком
Структура игры, бой, экономика, VIP, гильдии, админка — по исходному ТЗ (раздел 5); ТЗ является источником, здесь не дублируется.

## Приняты на этапе 0 (предложения инженера, подлежат подтверждению после обследования VPS)
1. **Сервер на Go, один статический бинарник**, без Docker: проще изолировать (systemd + отдельный пользователь), нет зависимостей. Docker не устанавливается.
2. **Префикс `/LunexGame/`** зашит в маршруты; корневые `/api`, `/assets`, `/admin` не используются (тесты это проверяют).
3. **Публикация через существующий nginx** (`location ^~ /LunexGame/`, include-сниппет), порт — loopback, выбирается при установке и проверяется на занятость. Новых публичных портов нет.
4. **Доставка по SSH с forced command** + `restrict`; пользователь `lunexgame-deploy`, sudo только на `systemctl restart lunexgame.service`. Host key закрепляется в секрете `DEPLOY_KNOWN_HOSTS`. Бинарник проверяется по SHA-256, релиз = commit SHA.
5. **Данные вне релизов**: `/opt/lunexgame/data|assets|backups` деплой не затрагивает.
6. **СУБД: SQLite (WAL), отдельный файл в /opt/lunexgame/data** (решено по обследованию: 1 vCPU/1.9 ГБ ОЗУ, чужая Postgres в контейнере agroapp не используется). Драйвер — чисто-Go (modernc.org/sqlite), CGO не нужен. Пересмотреть при росте нагрузки. БД — отдельная, `lunexgame_*`, не из интернета. Пока БД не подключена, `/api/health` её не заявляет.
7. **Основная ветка**: в репозитории нет ни одной ветки; workflow настроен на `main`. Нужно подтверждение.
8. **Автодеплой выключен по умолчанию**: job `deploy` запускается только при `vars.DEPLOY_ENABLED == 'true'` и environment `production`.
9. **Миграции**: только вперёд, неразрушающие применяются автоматически после бэкапа; разрушающие — вручную. Откат приложения не откатывает БД; каждая миграция совместима с предыдущей версией приложения (expand/contract).

## Этап 1
10. **Движок клиента: Godot 4.5-stable, рендерер GL Compatibility** (мобильный и веб-экспорт, малый размер). Обоснование подтверждено частично: Android-экспорт arm64 даёт 26 МиБ с пустой сценой; пригодность для 3D-боя и Web/PWA на iPhone **ещё не проверена прототипом**.
11. **Версия Godot закреплена в CI** (`GODOT_VERSION`); смена — отдельное решение.
12. **Целевое устройство разработки: iQOO 15R, Android 17** (со слов владельца). targetSdk сборки 35; совместимость с Android 17 проверяется только установкой на устройство.
13. **Подпись APK:** пока одноразовый debug-ключ CI (каждая сборка подписана новым ключом, обновление поверх установленной невозможно — удалять старую). Постоянный ключ нужен до функции обновления из игры.
14. **Гостевой токен** — 256 бит случайных, на сервере хранится SHA-256; в клиенте — в `user://` (песочница приложения). Лимит создания гостей: 10/мин на IP.
15. **Резервные копии БД** перед миграциями: `VACUUM INTO` в `/opt/lunexgame/data/backups` (служба имеет запись только в data/ и assets/).
16. **Godot переведён 4.5 → 4.7-stable** по решению владельца (быстрее). Run 41886913975 (commit 4138442): импорт, headless-вход клиента на настоящий сервер (BOOT_OK), экспорт Android APK и проверка размера ≤ 90 МиБ — пройдены. Скорость 4.7 относительно 4.5 не измерялась. Артефакт APK теперь из этого запуска.

17. **Ресурсы:** манифест `GET /LunexGame/api/assets/manifest` (путь, размер, SHA-256, группа = первый каталог пути; `start` — до входа, остальное в фоне), файлы `GET /LunexGame/assets/<путь>` с поддержкой Range. Публикуются только файлы внутри групповых каталогов `AssetsDir`; скрытые файлы и файлы в корне не публикуются; пути берутся из индекса, не из ФС. Диск перескандируется не чаще раза в 5 с.
18. **Заглушки ресурсов:** детерминированно генерируются сервером (не лежат в репозитории), помечены `placeholder:true`, перекрываются реальным файлом с тем же путём. Удалить после появления настоящих ресурсов.
19. **Докачка:** клиент качает файл кусками по 1 МБ с заголовком Range в `.part`; перед использованием проверяется SHA-256; `.part` от другой версии файла отбрасывается. Состояние — `user://assets_state.json`.
20. **Проверка целостности:** при обычном запуске — наличие и размер; полная перепроверка хэшей включается переменной `LUNEXGAME_VERIFY_FULL=1` (в игре — будет кнопка/условие позже). Решение о периодической полной проверке отложено.

21. **Бой (прототип):** сервер рассчитывает бой целиком в игровом времени (шаг 100 мс, лимит 90 с, без случайности — детерминированно) и отдаёт запись событий; клиент проигрывает. Главная способность в этой схеме срабатывает автоматически при полной энергии; ручной запуск по портрету потребует боя в реальном времени (этап 2). Выбрано владельцем 2026-11-04.
22. **Правила энергии, реализованные и покрытые тестами:** старт 0; растёт от нанесённого обычной атакой урона, полученного урона и фактически восстановленного здоровья (избыточное лечение не считается); главная способность тратит весь запас; её урон и лечение энергию владельцу не возвращают (получатели лечения энергию получают); коэффициенты — структура `Energy`, пока константы (вынос в админку — этап 5). Таймаут и взаимное уничтожение — поражение атакующего.
23. **Временный баланс `proto-1`:** 5 героев игрока и 5 врагов, здоровье ×3 для длительности ~50 с. Версия баланса записывается в бой (закрепление на старте). Не финальный контент.
24. **Хранение боёв:** таблица `battles` (миграция 0002), бой доступен только владельцу. Награды ещё не начисляются, поэтому защита от двойной награды пока не нужна и не проверена.

25. **Рендерер остаётся GL Compatibility** (решение владельца 2026-11-04): один рендерер для Android и Web (PWA работает только на нём), широкая совместимость. Сравнение с Vulkan не проводим; настройки качества (лимит FPS, масштаб разрешения) закладываются позже.
26. **PWA:** Web-экспорт без потоков (не нужны COOP/COEP), раздача `/LunexGame/play/`; PWA делается после Android-версии; iPhone-проверка — через владельца, когда будет развёрнута страница. Подробности и риски — docs/PWA_ASSESSMENT.md.

27. **PWA откладывается до этапа 6:** у владельца нет iPhone, проверять некому; тестовая выкладка сейчас смысла не имеет. Работы к тому моменту: сжатие ядра, автодеплой Web-сборки, русская офлайн-страница, иконки, замер памяти при реальных ресурсах (docs/PWA_ASSESSMENT.md).
28. **Безопасная зона:** весь интерфейс размещается внутри отступов `DisplayServer.get_display_safe_area()` (класс SafeArea) — вырез камеры, скруглённые углы, системные жесты. Новые экраны обязаны использовать SafeArea (требование к интерфейсу). Владелец заметил перекрытие таймера камерой на iQOO 15R.

29. **Постоянный ключ APK:** создаётся владельцем на VPS через openssl (PKCS12), приватный ключ в переписку и репозиторий не попадает; хранится в секретах окружения GitHub `android-signing` (только ветка main) + резервная копия у владельца. Release-APK подписывается только на push в main; в CI сверяется SHA-256 сертификата с переменной `ANDROID_CERT_SHA256`. `versionCode` = номер запуска CI. Процедура — docs/SIGNING.md.

30. **Движение героев в бою (этап 2), решение владельца 2026-11-04:** как в AFK Arena. Ближний боец подбегает к цели один раз и остаётся рядом, пока цель жива; после её гибели выбирает следующую и бежит к ней. После каждого удара не возвращается. Дальнобойные герои (стрелок, маг, целитель) стоят на месте.
    - **Расчёт на сервере.** Позиции и движение — часть состояния боя: у героя есть скорость бега и дистанция атаки; атака возможна только в зоне досягаемости, перебежка занимает игровое время. Бой остаётся детерминированным. В записи боя появляются события движения (откуда, куда, когда), клиент их проигрывает.
    - **Несколько атакующих одной цели** занимают разные точки вокруг неё, чтобы герои не слипались.
    - **Главная способность:** ближний герой сначала занимает позицию возле цели, дальнобойный применяет с места («перемещения для атак и применения способностей» из ТЗ).
    - **Визуально:** при каждом ударе короткий «выпад» на месте (без пробега туда-обратно) для ощущения удара.
    - **После боя** герои возвращаются на стартовые места (победная стойка).
    - **Текущий прототип (этап 1)** с возвратом после каждого удара — временный; движение там чисто визуальное и на расчёт не влияет. Заменяется на этапе 2.
    - **Причины выбора:** читаемость узкого вертикального поля, меньше анимаций и нагрузки на слабых телефонах, перемещение становится частью механики (дальние цели достаются позже).

## Этап 2
31. **Первая часть движения, 2026-11-04, commit `a2b5b61`:** расширение существующего детерминированного расчёта, без смены схемы деплоя и без миграции БД. Реальный ход боя по соединению будет следующими частями; сейчас `Run` по-прежнему возвращает полную запись.
    - **Координаты:** целые `position: {x,z}` в тысячных долях единицы Godot; стартовые места соответствуют расстановке клиента (2 передних + 3 задних). `attackRange` — в тех же единицах, `runSpeed` — в единицах координат в секунду. Нулевые значения при подготовке серверного отряда заменяются временными параметрами: дальность 1100 для ближних / 12000 для дальних, скорость 3000. Версия временного баланса — `proto-2-movement`; исходные определения отряда не меняются при расчёте.
    - **Цели и подход:** сохранён приоритет прототипа (передний ряд, затем номер слота, затем порядок входного списка); ближний удерживает выбранного противника до его гибели. Союзники резервируют разные направления на кольце вокруг цели (до пяти героев). Ближний сначала завершает подход, затем атакует/тратит энергию главной способности; перезарядка начинается с фактического действия. К неподвижной цели повторно не бегает. Если живая цель перемещается вне занятой позиции, боец следует за ней. Взаимно сближающаяся пара останавливается при контакте, чтобы не обходить друг друга бесконечно. Дальние не бегают; все поражаемые/лечимые цели проверяются по дальности, включая главные способности.
    - **Тик 100 мс:** цели выбираются до перемещения, новые позиции всех героев вычисляются по общему снимку, затем происходят атаки и смерти. Порядок обработки атак остаётся порядком входного списка, как в прототипе; новая модель одновременного разрешения урона в эту часть не входит. Округление координат сохраняет остаток пути (очень медленный герой не застревает); погрешность длины отдельного шага меньше 2 тысячных единицы, суммарный путь ограничен бюджетом скорости.
    - **Запись:** событие `move` содержит `src`, время начала `t` и `move: {from,to,durationMs,target}`. Отрезки идут по тикам, атаки используют координаты в конце тика; `positions` в результате — конечные координаты до победной стойки. Старые записи в БД сохраняются без пересчёта. Клиент интерполирует серверные отрезки по игровому времени, даже если за кадр прошло несколько тиков. Выпад меняет только меш героя; после боя выжившие возвращаются на стартовые места визуально.
    - **Граница части:** нет навигации вокруг препятствий/общего разрешения столкновений (пути могут пересекаться); новый бой требует обновлённого клиента для правильного отображения движения. Автонавыки, пассив, ручная способность, WebSocket и переподключение ещё впереди. Проверены повторные чтения и старты боя: GET возвращает ту же запись, повтор POST создаёт отдельную бесплатную попытку. Начислений наград/расходов нет; отклонение несуществующих клиентских `finish`/`claim` проверено, но это **не** проверка однократности будущих наград. Для них обязательны транзакция и отдельные тесты повторных/конкурентных запросов до включения начислений.

32. **Автонавыки и пассив, 2026-11-04, commit `fef1d38`:** первая реализация двух настраиваемых автоматических слотов и одного пассива характеристик. Эффекты и числа временные, а не утверждённый контент. Редкость не участвует в расчёте силы.
    - **Данные:** уровень героя (`0` в старых серверных определениях означает 1, предел по умолчанию 100); у автонавыка ID/название, уровень открытия, перезарядка, эффект `damage/heal`, правило цели, сила в тысячных долях атаки и улучшения `{level,powerPermille}`. Выбирается улучшение с наибольшим достигнутым уровнем, порядок списка не важен. Все действия используют дальность героя. Пассив содержит уровень открытия, прибавку к атаке/MaxHP в тысячных долях базового значения и улучшения бонусов. Неизвестные эффекты/цели, неверные уровни, повторные пороги/ID и недопустимые числа отклоняются при создании боя.
    - **Применение:** по умолчанию открытие автонавыков на 10/20, пассива на 40 задано в серверных определениях. Пассив однократно меняет характеристики при создании боя, герой начинает с полным эффективным MaxHP и нулевой энергией. `Outcome.units` уже содержит эффективные характеристики; клиент не применяет бонус второй раз. `New` принимает базовые серверные определения, не список эффективных характеристик из результата другого боя.
    - **Планировщик:** не больше одного действия героя за тик 100 мс; приоритет — полная энергия/главная способность, автонавык 1, автонавык 2, обычная атака. У каждого автонавыка собственная перезарядка: первое применение не раньше её длительности от начала боя, последующие — от фактического применения. Обычные атаки её не сбрасывают. При отсутствии цели в дальности или при избыточном автолечении перезарядка не тратится; проверяются следующие действия. Ближний сначала завершает подход к удерживаемой цели. Главная способность остаётся на полном автомате, расходует всю энергию и сохраняет правила решения 22.
    - **Цели:** удерживаемый противник (для дальнего — приоритет переднего ряда/слота), противник с минимальным абсолютным HP, все противники в дальности, себя, союзник с минимальной долей HP или все союзники в дальности. Равенство разрешается порядком входного отряда. Мёртвые исключены, воскрешения нет. Энергия растёт от фактического урона обычных атак и автонавыков, полученного урона и фактического автолечения; получатель автолечения тоже получает энергию, самолечение учитывается один раз. Избыточное лечение не даёт энергии. Урон/лечение главной способности владельцу энергию не возвращают.
    - **Пошаговое ядро:** `New` закрепляет копии определений, вложенных улучшений, коэффициентов и версии баланса; `Step` продвигает один игровой тик, `Snapshot` возвращает копию текущего состояния, `Outcome` выдаёт копию записи только после завершения. `Run` использует то же ядро до результата. Повторный `Step` после результата ничего не меняет и не выдаёт событий; разные бои не делят таймеры/бонусы. Один экземпляр принадлежит одному исполнителю; сетевой цикл и многопоточный доступ к одному бою ещё не реализованы. Публикации через админку пока нет; тестируется изоляция конфигурации на уровне ядра.
    - **Демо `proto-3-skills`:** оба отряда уровня 40, чтобы проверять все открытия. Танк: удар по своей цели и самолечение; боец: два усиленных удара; стрелок: удар по слабой цели и залп; маг: массовый удар и удар по слабой цели; целитель: лечение самого раненого и группы. Пассив танка — +10% MaxHP, остальных — +10% атаки; на уровне 70 бонус становится +20%. Первый автонавык усиливается на 30, второй — на 50 (сила ×1,2). Это временные параметры, прогресс/уровни аккаунта ими не изменяются.
    - **Запись и клиент:** `auto_skill` содержит `skillId`, слот 1/2, тип эффекта и фактические цели; `passive` в t=0 подтверждает уже применённый бонус. Клиент использует общую анимацию навыка, сверяет порог, перезарядку, ID и однократность пассива. Старые записи не пересчитываются, миграций нет. Для корректного отображения автолечения нужен новый APK. Ручная способность, WebSocket/переподключение, скорости и начисления наград остаются следующими частями; защита от двойной награды не считается проверенной.

33. **Скорости боя, 2026-11-05:** сервер остаётся источником прав на x1/x2/x4. x1 доступна сразу, x2 появляется после `tutorial_completed`, x4 при `vip_level >= 2`; клиентские поля обучения/VIP отклоняются. Права вынесены в `account_progress`, скорость сохраняется в `battles.speed` миграцией 0003. HTTP пока отдаёт полную запись: переключение меняет только скорость проигрывания, повторный PUT идемпотентен и не создаёт награды или новый бой. Выдача обучения/VIP и живое управление остаются отдельными задачами.
34. **Разведение героев, 2026-11-05:** минимальная дистанция живых героев задаётся параметром баланса `MinHeroDistance` (по умолчанию 600 в координатах поля). При подходе сервер выбирает первую свободную точку из фиксированного списка, затем проверяет расстояние к уже размещённым героям в порядке отряда. Случайность и выход за радиус атаки запрещены; клиент скрывает имена 3D-моделей, оставляя полосы и числа читаемыми. Значение временное и требует визуальной проверки на телефоне.
35. **Живой бой, 2026-11-05:** первый серверный контур WebSocket использует тот же детерминированный `Battle.Step` с тиком 100 мс. Команда ручной главной способности принимается только для живого героя с полной энергией; при обрыве соединения сессия продолжает полный автомат в памяти и новое соединение получает снимок. Контент из админки и награды пока не подключаются.
36. **JSON-числа в клиенте, 2026-11-05 (D1):** Godot разбирает числа JSON как float. Перед `Array.has` и сравнением с `int` (кнопки скоростей и любые будущие целочисленные поля ответа) значения приводятся через `int()`. Иначе разрешённая сервером кнопка выглядит и ведёт себя как выключенная.
37. **Жизненный цикл живого боя, 2026-11-05 (D2):** соединение само бой не создаёт — нужно сообщение `start`. Незавершённый бой аккаунта при новом соединении продолжается (снимок, `resumed`). Завершённый без соединения хранится 2 минуты (чтобы показать результат), затем удаляется; `start` заменяет его новым боем сразу. Одновременно не больше одного боя на аккаунт и 32 на процесс (1 vCPU, ~2 ГБ); сверх лимита — `busy`, сессия не создаётся. Наград пока нет.
38. **Ручная главная способность, 2026-11-05 (D3):** по умолчанию полный автомат (как запись HTTP). Сообщение `set_auto` выключает автомат только у героев игрока: главная способность ждёт `main_skill`. Враги всегда на автомате. При обрыве связи сервер включает принудительный автомат, не меняя выбор игрока; после переподключения снова действует выбор. Автонавыки и обычные атаки не ждут кнопки.
39. **Команда только своим героям, 2026-11-05 (D4):** `RequestMainSkill` принимает id только живого героя стороны `player` этого боя с полной энергией. Враг, мёртвый, чужой id и неполная энергия — отказ, флаг ручного запуска не ставится.
