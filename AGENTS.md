# AGENTS.md — LunexGame («Самрая: Пробуждение легенд»)

Инструкции для ИИ-агентов, продолжающих разработку. Язык общения, документации и комментариев — **русский**.
Проект ведётся поэтапно; состояние на **2026-11-04**: этапы 0 и 1 выполнены, следующий — **этап 2** (боевая система).

## 1. С чего начинать каждую сессию
1. Прочитать: `docs/SPEC.md` (полное ТЗ), `docs/ROADMAP.md`, `docs/DECISIONS.md`, `docs/PROGRESS.md`, `docs/DEPLOYMENT.md`.
2. Продолжать с первого незавершённого пункта ROADMAP. Не начинать все модули сразу — небольшие завершённые части.
3. В конце: обновить ROADMAP (отметка `[x]` только после реализации **и проверки**, с датой, commit, способом проверки и ограничениями), PROGRESS, DECISIONS; сообщить результат, проверки, ограничения и следующий конкретный шаг.

## 2. Правила качества
- Не утверждать, что что-то работает, пока это не проверено запуском/тестами. Явно писать, что **не** проверено.
- Не скрывать ошибки заглушками. Временные модели/баланс помечать как временные.
- Все расчёты результата боя, наград и расхода ресурсов — **только на сервере** (клиент не авторитетен).
- Тестировать критические сценарии: повторные запросы, двойные награды, расход ресурсов, обрывы связи, публикация баланса, неудачный деплой.
- Не добавлять скрытые множители редкости и функции вне текущего этапа (см. `docs/SPEC.md`, раздел «следующая дорожная карта»).
- Не коммитить секреты. Секреты — только GitHub Secrets/окружение VPS. Не просить присылать приватные ключи в переписку.

## 3. Безопасность инфраструктуры (обязательно)
- VPS `144.31.254.99`, домен `tts-ufa.ru`, проект живёт под **`https://tts-ufa.ru/LunexGame/`** (регистр важен). На VPS работают **чужие проекты** (agroapp, ufagame, pocketbase, VPN, CasaOS, rik-agro-*): не останавливать, не менять, не занимать их пути и порты.
- **У агента нет доступа к VPS.** Любые изменения на сервере — только через CI-деплой (`.github/workflows/ci-deploy.yml`). Всё, что требует действий на VPS, оформлять как точные инструкции владельцу (он выполняет сам под root) и ждать подтверждения.
- Не использовать корневые пути `/api`, `/assets`, `/admin` — только под префиксом `/LunexGame/`.
- Не менять DNS, сертификаты, SSH-порт, firewall, не обновлять ОС/пакеты, не чистить Docker глобально, не заменять конфигурацию nginx целиком (подключён один `include snippets/lunexgame.conf`).
- Службы и каталоги — с префиксом `lunexgame` (`/opt/lunexgame`, служба `lunexgame.service`, порт `127.0.0.1:18741`).
- Отдельный пользователь доставки `lunexgame-deploy` с ограниченными правами (forced command). Не расширять его права.

## 4. Устройство репозитория
- `server/` — Go-сервер (`go.mod` задаёт версию Go). `internal/app` (HTTP), `internal/store` (SQLite + миграции в `internal/store/migrations`), `internal/assets` (манифест/раздача ресурсов), `internal/battle` (расчёт боя).
- `client/` — Godot **4.7-stable**, рендерер GL Compatibility, портретный экран 1080×1920. Скрипты в `client/scripts` (`boot.gd`, `asset_loader.gd`, `battle.gd`, `safe_area.gd`, `session.gd`).
- `tools/smoke-assets.sh` — интеграционная проверка клиент↔сервер (вход, загрузка ресурсов, докачка, повреждения, бой).
- `deploy/server/` — файлы установки на VPS (выполняет владелец). `.github/` — CI и общее действие `setup-godot-android`.
- `docs/` — документация (ROADMAP, DECISIONS, PROGRESS, DEPLOYMENT, SIGNING, PWA_ASSESSMENT, ASSETS, SPEC).

## 5. Как собирать и проверять
- Сервер: `cd server && gofmt -l . && go vet ./... && go test -race ./...` (для `-race` нужен cgo; без него `CGO_ENABLED=0 go test ./...`). Сборка: `CGO_ENABLED=0 go build ./cmd/lunexgame`. Локальный запуск: `LUNEXGAME_LISTEN=127.0.0.1:18741 LUNEXGAME_DB=/tmp/x.db go run ./cmd/lunexgame`. Сервер **обязан слушать только loopback**.
- Godot 4.7: бинарник и шаблоны экспорта — `https://github.com/godotengine/godot-builds/releases/download/4.7-stable/Godot_v4.7-stable_linux.x86_64.zip` и `..._export_templates.tpz` (шаблоны ~1,2 ГБ, нужны только для экспорта). Импорт: `godot --headless --path client --import`.
- Интеграционная проверка: `tools/smoke-assets.sh <путь к godot> <путь к бинарнику сервера>` (все сценарии должны пройти).
- Визуальная проверка кадров без экрана: `xvfb-run` + `--rendering-driver opengl3 --write-movie ... --fixed-fps 20` (Mesa llvmpipe). Для проверки выреза: `LUNEXGAME_FAKE_SAFE_TOP=110`.
- В headless-режиме Godot не рисует; значит, внешний вид проверять кадрами или на телефоне.

## 6. CI/CD (важно)
- **Push в `main` разворачивает серверную часть на боевом VPS автоматически** (после проверок), с откатом на прежнюю версию при провале health. Поэтому: работать в ветках и PR, в `main` сливать только проверенное.
- **Владелец разрешил агенту самому сливать готовые PR в `main` после успешных проверок (2026-11-04), без повторного подтверждения.** Прямой push в `main` не использовать; после слияния проверить CI-деплой и публичные version/health. При ошибках проверок или конфликтах сначала устранить проблему.
- `ci-deploy.yml` (gofmt/vet/test → деплой только при `vars.DEPLOY_ENABLED=true`, окружение `production`, пути `client/**`, `docs/**`, `*.md`, `tools/**`, `.github/actions/**` деплой не вызывают). `client-android.yml` (smoke-тест, debug-APK, проверка release-экспорта одноразовым ключом, Web-экспорт, задача `release-apk` с **постоянным ключом** — только push в `main`, окружение `android-signing`, см. `docs/SIGNING.md`).
- Миграции БД: только вперёд, **аддитивные и совместимые с предыдущей версией приложения** (откат кода не откатывает БД). Разрушающие миграции автоматически не выполнять. Перед миграцией сервер сам делает копию (`VACUUM INTO`).
- Данные игроков, загруженные ресурсы и опубликованный баланс деплой перезаписывать не должен (они вне каталога релизов).

## 7. Ловушки, которые уже встречались
- GDScript: имя метода `_get` занято движком; проверять константы (`SIZE_SHRINK_CENTER`); `class_name` + статические переменные для общего состояния; после правок скриптов запускать `--import` и смотреть `SCRIPT ERROR`.
- YAML GitHub Actions: в `name:` шага нельзя «: » без кавычек.
- Go `http.FileServer` перенаправляет `/index.html` (ломает service worker) — для PWA использовать прямую отдачу.
- Не использовать `pkill -f` шаблон, совпадающий со своей же командой.
- Интерфейс: **все экраны обязаны учитывать безопасную зону** (`SafeArea`, вырез камеры) — решение 28.
- Android: `versionCode` берёт CI из номера запуска; без постоянного ключа новая сборка не ставится поверх старой.
- Web (PWA): `user://` живёт в памяти и зеркалируется в IndexedDB — риск для больших ресурсов (`docs/PWA_ASSESSMENT.md`).

## 8. Следующая задача — этап 2 (боевая система)
Опираться на решения 21–24, 30 в `docs/DECISIONS.md`. Порядок:
1. Серверное ядро боя с **позициями и движением** (решение 30: ближний подбегает один раз и остаётся рядом, пока цель жива; дальнобойные стоят; несколько атакующих встают в разные точки вокруг цели; дистанция атаки, скорость бега, детерминированность).
2. Остальная механика по ТЗ: два автоматических навыка (открываются на уровнях 10/20 — в боевом ядре параметры настраиваются), пассив (уровень 40), полный автомат, энергия (правила в решении 22), таймер 90 с, скорости x1/x2/x4, цели выбираются автоматически по правилам навыка.
3. Соединение (WebSocket под `/LunexGame/…`, учесть, что nginx уже передаёт Upgrade): ручная главная способность по нажатию на портрет, переподключение, продолжение боя на сервере на полном автомате при обрыве, награды однократно, версия баланса закрепляется на старте боя.
4. Клиент: проигрывание боя в реальном времени, нажатие на портрет, события движения.
Каждая часть — с тестами на сервере и интеграционной проверкой (расширять `tools/smoke-assets.sh` или добавить рядом) и обновлением документов.

## 9. Что нельзя без отдельного решения владельца
Менять рендерер, версию Godot, структуру префикса `/LunexGame/`, схему деплоя/ключей, добавлять платежи, арену, чат, экипировку, призыв, конструктор интерфейса (всё это — «следующая дорожная карта»). Реальные модели и иллюстрации ещё не предоставлены — использовать явно помеченные временные.
